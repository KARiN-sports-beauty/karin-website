# KARiN.chatbot テスト仕様書

## 1. 目的

KARiN.chatbotが、

- 正しいKnowledgeを使える
- 自然な日本語を理解できる
- KARiN.固有情報を捏造しない
- 適切なサービスを提案できる
- 医療安全を守れる
- 予約システムとKnowledgeを混同しない
- 過度に予約へ誘導しない

ことを検証する。

---

# 2. RAG回帰テスト

既存のRAGテスト1〜5は、
今後の変更後も検証意図を維持し、基本的にPASSすること。

`source_key` 追加はRAG再構築ではない。
Embeddingモデル、検索SQLの意味、`match_ai_knowledge` の既存挙動は変えない。

`scripts/test_ai_knowledge_rag.py` は、
production Knowledgeをupsertしてテストする方式をやめる。

- テスト1〜3は既存Knowledgeを読み取り、検索結果を検証する
- テスト4は、既存の inactive 行があれば読み取り、検索結果に含まれないことを確認する。
  本番公式Knowledgeの status は変更しない。テスト用データの INSERT もしない
- テスト5は、本番へテスト用KnowledgeをINSERTしない。
  同期済みの active 公式Knowledgeを `source_key` で特定し、検索できることを確認する
- 自然なユーザー発話でも、既存の本番公式Knowledgeを読み取り専用で検索する
- `source_key` 追加後は、必要に応じてテスト対象を `source_key` で安定して特定する

titleはidentityとして使わない。
テストのために本番公式Knowledgeのtitle / content を上書きしてはいけない。
テスト実行中、本番 `public.ai_knowledge` への INSERT / UPDATE / DELETE / Embedding保存は行わない。

## NOTES-構成

②の初期構成は設計上7件。
`notes_avoid_over_referral` は独立行を作らず `notes_medical_safety` に統合する。
実装時の投入は6件。

| source_key | テストで確認したいこと |
|---|---|
| `notes_body_connection` | 局所＝原因と断定しない。毎回同じ標語を入れない |
| `notes_undecided_consultation` | いきなりメニューを決めつけない。質問は1〜2個 |
| `notes_suggestion_stance` | 候補として提案する。効果保証しない |
| `notes_approach_candidates` | 目的に応じた候補。料金・可否は①に任せる |
| `notes_reservation_intent` | 相談だけには予約を勧めない |
| `notes_medical_safety` | 緊急は医療機関優先。一般相談を一律に病院へ送らない |

`notes_clarifying_questions` および `notes_avoid_over_referral` を
独立Knowledgeとして検索・投入しない。

安全ルールは②の検索ヒットに依存させない。

# 11. 会話品質

以下を評価する。

- 回答が質問に直接答えている
- 不必要な質問をしない
- 1回の回答で質問しすぎない
- 1〜2個程度の追加質問に留める
- 説明が長すぎない
- スマートフォンで読みやすい
- 押し売りしない
- 不安を煽りすぎない
- 過剰な絵文字を使わない

---

# 12. サービス提案品質

サービス提案は、

- ユーザーの相談内容に関連している
- Knowledgeに基づいている
- 診断になっていない
- 効果を保証していない
- 選択肢として提示している

こと。

# 13. 予約誘導品質

予約案内は、

- ユーザーが予約したい場合
- サービスを受けたい意思を示した場合
- 会話上自然に予約へ進む場合

に行う。

すべての回答に予約CTAを付けない。

`show_booking_cta` は初回の予約意図に対してのみ true とする。チャット予約の条件入力開始後、空き候補表示、confirming、guest_info では false とする。

## BOOK-CTA-01

入力：「予約がしたいです」

期待：初回予約案内（『ご予約』ボタン、Web予約へ進む、このまま会話で予約を進める、エリアと施術時間）。ユーザー向け文言に「ヘッダー」は出ない。`show_booking_cta: true`。直後に「ご希望のエリアと施術時間を教えてください。例：東京・90分」を重複表示しない。

## BOOK-CTA-02

上記のあと「東京」など条件入力が始まったら `show_booking_cta: false`。

## BOOK-WINDOW-01

入力：「直近で18時〜取れるところ」（エリア・施術時間済み）

期待：日付を聞き返してループしない。`time_from=18:00`。近い将来の候補を既存枠算出で検索する。

## BOOK-EXPAND-01

入力：平日の候補提示後に「他の平日は空いてないん？」

期待：前回の候補日を再表示しない。既存枠算出を、提示済み日を除いた平日で再実行する。本当に他になければその旨を伝える。`time` / `time_from` は維持する。

## BOOK-GATE-01

入力：身体相談のあと「予約したいです」→「90分」→「来週の土日は？」

期待：area 未確定のあいだは `list_web_booking_slots()` を呼ばない。90分だけでは空き検索しない。来週の土日は現在日基準で具体日付（例: 2026-09-09 なら 2026-09-19 と 2026-09-20）へ変換し、エリアだけ確認する。LLM が ◯月◯日 などのプレースホルダーや架空枠を出さない。東京と答えたら既知の90分・来週土日を再質問せず実データだけ表示する。

## BOOK-BANDS-01

入力：平日の夜（90分）。既存枠の開始可能時刻から連続区間を組む。

期待：

- 1日に独立した空き区間が複数ある場合はすべて表示する（1日1区間に潰さない）
- 空き区間の終了は last_start＋施術時間。最終開始可能時刻と混同しない
- 90分で 18:00〜26:00 空いている日を 18:00〜25:15 に短縮しない
- 18:00〜20:00 と 21:00〜26:00 のように飛びがある開始列は連結しない
- 「夜」を 19:00 に固定変換しない。既存の予約可能開始時刻から夜の時間帯を抽出する
- 個人予定（personal）・休憩・帯同は前後60分バッファなし。既存の出張予約のみ前後60分
- シフト 19:00〜26:00・personal 21:00〜24:00・90分なら、開始可能は 19:00〜19:30 と 24:00〜24:30。チャットの空き区間表示は 19:00〜21:00 と 24:00〜26:00。空き区間の終了と最終開始可能時刻は別概念

## BOOK-GUEST-01

入力：confirming 後の guest_info で「藤田幸士」

期待：`guest_last_name` / `guest_first_name` に自動分割して保存しない。姓と名を改行する例で確認する。予約は作成しない。

## BOOK-GUEST-02

入力：「姓：藤田、名：幸士、090-1234-5678、test@example.com、東京都渋谷区○○」（出張）

期待：4項目を一度に保存し、追加質問せず最終確認へ進む。その「はい」で既存の予約確定処理へ進む。空白区切りの「藤田 幸士」も姓名として認識する。ラベルなし5行（藤田 / 幸士 / 電話 / メール / 出張先）も同様に全項目を保存する。

## BOOK-GUEST-03

「藤田幸士、090-1234-5678、test@example.com」→ phone / email は保存し、姓名だけ確認する。既に入っている項目は再質問しない。現在のチャット予約は出張のみなので、院内を予約選択肢として案内しない。`guest_fields_for_place("in_house")` は将来用に3項目のまま残す。

## USAGE-01

入力：動的選択肢の表示とクリック、自由入力、予約開始、予約完了（create はモック）

期待：`chatbot_usage_logs` 相当の記録に choice_set / shown_choices / selected_choice / input_type / intent 遷移 / booking_started / booking_completed が入る。自由入力本文・氏名・電話・メールは保存しない。分析INSERT失敗でも応答と予約完了は成功する。既存C0〜C9・選択肢生成・RAG・予約判定は変えない。

## USAGE-02

入力：管理画面の利用分析ダッシュボード。0件・1件・複数conversation・期間フィルタ。

期待：総会話数 / 予約開始 / 予約完了 / 完了率（0件除算なし）/ intent別 / choice_set別 / selected_choice別が正しい。`selected_choice` は前ターンの `choice_set` に紐づける。同じ行の `choice_set` と JOIN しない。会話全文・個人情報は出さない。分析読み取り失敗でも `/api/chat` と予約は止まらない。既存C0〜C9・選択肢・RAG・予約処理は変えない。管理者認証の配下のみ。

AI自動分析・改善案生成・自動CHOICE_SETS変更は USAGE-02 の対象外。実データ蓄積後の将来項目とする。詳細は `docs/KARIN_AI_SPEC.md` の 24。

## CHOICE-01

入力：「鍼と整体、どちらが合いそうですか？」

期待：コード定義の目的選択肢（痛み・疲労・姿勢・バランス＋その他・自由に相談）が出る。LLMが選択肢を作らない。「痛みを軽減したい」は通常発話として処理し、鍼に自動決定しない。緊急・guest_infoでは相談用選択肢を出さない。予約最終確認では相談用CHOICE_SETSは出さず、「はい、予約を確定する」のみ出してよい。ユーザー向け文言に「ヘッダー」は出ない。

# 16. テスト失敗時の対応

テストが失敗した場合、

1. 入力
2. 実際の回答
3. 期待される回答
4. 使用されたKnowledge
5. Retrieval結果
6. Prompt
7. モデル出力
8. 安全判定
9. 予約システム連携

を確認し、
どこに問題があるかを特定する。

テストを弱くして成功扱いにしない。

# 17. 実ユーザーを想定した評価

今後実際のユーザー会話が蓄積された場合、
個人情報等を適切に除いたうえで、
実際の自然な表現をテストケースに追加する。

人工的な質問だけではなく、
実際のユーザーが使う曖昧な表現・口語表現を重視する。
