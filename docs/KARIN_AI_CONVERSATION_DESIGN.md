# KARiN.chatbot 会話ロジック設計書

## 文書の位置づけ

本書は、KARiN.chatbot の **AI会話ロジック** の設計である。

正式な開発基準は次と併用する。

- `.cursor/rules/karin-ai-development.mdc`
- `docs/KARIN_AI_SPEC.md`
- `docs/KARIN_AI_TEST_SPEC.md`

本書が扱うのは「ユーザーの相談を理解し、必要な Knowledge を選び、自然な回答を返す」処理である。

予約獲得より、まず相談にちゃんと答えることを優先する。

本書作成時点では **実装しない**。レビュー後に実装工程へ進む。

# 3. 今後の理想的な処理フロー

仕様書の直線フローを基本とし、次を加える。

- 安全判定は RAG より前のゲートである
- 意図は毎ターン再評価する（最初の判定で固定しない）
- RAG クエリは「直前の一文」だけでなく、会話で分かっている要点を足して作る
- 予約は別経路であり、全回答の終点ではない
- 生成後に、捏造・CTA・質問数の軽い検査をする

```text
ユーザー入力 ＋ 会話状態（履歴・既知の事実）
↓
A. 入力の正規化（短文・指示・続きの補完）
↓
B. 安全ゲート（ルール。RAGに依存しない）
    ├ 緊急 → 医療機関優先の回答。予約誘導しない。必要ならここで終了
    └ 非緊急 → 続行
↓
C. このターンの intent を再評価（複合可）
↓
D. 必要な source_type を選ぶ（固定順位なし）
↓
E. RAGクエリを組み立てて検索
    ※ RPCは当面変更しない。多めに取り、アプリ層で種別を活かす
↓
F. コンテキスト組み立て
    - 常時適用のAIルール（system）
    - 会話履歴
    - 既知の事実（部位・期間・目的など）
    - 取得した Knowledge（①事実 / ②判断軸 / ③一般健康）
    - 予約が必要なら予約システムの結果（Knowledgeではない）
↓
G. 回答生成（Chat Completions）
↓
H. 出力検査
    - 公式事実の捏造がないか
    - 診断・保証になっていないか
    - 追加質問が1〜2個を超えていないか
    - 不要な予約CTAがないか
↓
I. 会話状態の更新（intent、聞いたこと、分かったこと）
↓
J. 予約意図が明確なときだけ予約導線
```

RPC に source_type 条件を足すのは、必要が実証されてから検討する。現時点では既存 `match_ai_knowledge` を維持する。

# 4. intent / consultation type の考え方

intent は排他的な1ラベルにしない。1ターンに複数あってよい。毎ターン、最新発話と履歴から付け直す。

## 4.1 主な種別

| intent | 例 | 主な Knowledge |
|---|---|---|
| `emergency` | 急な片麻痺、胸痛、呼吸困難 | 安全ルール必須。② `notes_medical_safety` は補助 |
| `body_consultation` | 腰が痛いです | ② `notes_body_connection` ほか |
| `self_care` | 腰を温めたら良いですか | ② body_connection。③は将来 |
| `undecided_menu` | 何を受ければいいかわからない | ② undecided ＋ 必要なら① |
| `treatment_choice` | 鍼と整体どっち | ② suggestion / approach ＋ 必要なら① |
| `official_fact` | 料金、時間、初回割引、院内可否 | ①のみ |
| `health_general` | 睡眠不足の一般的影響 | ③。未投入中は捏造しない |
| `consult_only` | 相談だけしたい | ② reservation_intent |
| `booking_intent` | 予約したい | 予約フロー。①は方法の補助 |
| `availability` | 明日の夜空いてますか | 予約システム。Knowledgeで空いていると言わない |
| `smalltalk_or_other` | あいさつ等 | ルールのみ。無理に施術提案しない |

## 4.2 複合の例

「肩がつらい。料金は？」→ `body_consultation` ＋ `official_fact` → ②＋①

「相談してから予約するか決める」→ `consult_only` が先。予約CTAを出さない。

## 4.3 途中で変わる例

```text
腰が痛いです          → body_consultation
何分コースがありますか → official_fact が加わる
受けてみたいです       → booking_intent に遷移
明日空いてますか       → availability
```

最初が相談だから最後まで相談、にはしない。

## 4.4 判定方法（実装時の方針）

最初から重い分類モデルを必須にしない。

1. 緊急はキーワード／パターンで先に拾う
2. 予約・空き・料金・時間などは比較的規則で拾える
3. 曖昧な身体相談は、生成モデルに短く intent を出させるか、RAG後のプロンプトで扱う
4. 誤分類しても、安全ルールと「断定しない」ルールで被害を抑える

intent は内部状態であり、ユーザーにラベル名を見せない。

# 5. safety判定の位置

## 5.1 位置

**RAGより前**。ヒットしなくても安全ルールは消えない。

緊急時は、施術提案・予約誘導をしない。必要なら Knowledge 検索を省略してよい。

## 5.2 緊急の例（診断基準ではない）

- 強い胸痛
- 呼吸困難
- 意識障害・意識がおかしい
- 突然の激しい頭痛
- 片側の麻痺・脱力
- ろれつが回らない
- 重大な外傷
- 大量出血
- 急激な症状悪化

「予約を優先してはいけない状況」の判断材料である。病名は付けない。

## 5.3 過剰誘導をしない

肩こり・慢性の腰痛など、緊急性のない一般相談を自動で病院へ送らない。

受診の検討は、経過・急変・随伴症状があるときに出す。不安を煽らない。

## 5.4 実装上の分担

| 層 | 役割 |
|---|---|
| アプリの固定ルール | 緊急パターン、予約禁止、診断禁止 |
| system prompt | 同じ禁止を毎ターン適用 |
| ② `notes_medical_safety` | 考え方の補助。検索成功に依存しない |

# 6. source_type選択の考え方

固定順位 `official > notes > health` は作らない。

選択は回答生成の前、アプリ層で行う。RPC の検索条件には、当面使わない。

## 6.1 対応

| ユーザーの状況 | 使う種別 |
|---|---|
| 店・料金・時間・エリア・キャンペーン・予約条件 | ① |
| 部位の悩み、温め等のセルフケア相談 | ②中心。③は将来。メニュー事実が要れば① |
| メニュー未決定 | ②必須。必要なら① `treatment_policy` / `approaches` |
| 鍼と整体どちら | ②必須。定義・料金は① |
| 一般健康の仕組み | ③。未投入なら「確認できない」 |
| 相談だけ | ② `notes_reservation_intent`。予約CTAなし |
| 空き枠 | Knowledgeではなく予約システム |
| 緊急 | 安全ルール優先 |

## 6.2 RAG結果の使い方

RPC は全 active を返す。アプリ層で、

- 選んだ source_type を優先してコンテキストに載せる
- 選んでいない種別は、明らかに有用なときだけ残す
- ②の本文をユーザー向け解説として貼り付けない。判断軸としてモデルに渡す
- ①の事実だけを「公式情報」として使ってよい

## 6.3 ③が0件のあいだ

`health_general` でも一般論をモデルの知識だけで断定しない。  
「現在の公開Knowledgeでは一般健康の詳細を確認できない」と伝え、②の相談方針（断定しない、1〜2問）は使ってよい。

# 7. RAG検索の位置

安全ゲートと source_type 選択のあと、回答生成の前。

## 7.1 クエリ

生の最終発話だけにしない。短い発話（「はい」「腰です」）は、既知の部位・目的を足す。

例：履歴が「腰が痛い」＋今回「温めたら良い？」  
→ 検索文は「腰痛 温める 姿勢 動作 周辺」などに寄せてよい。

## 7.2 件数

会話では `match_count` を 8〜10 程度取り、アプリ層で間引く想定。  
RPC の意味は変えない。

## 7.3 使わないこと

- source_key を検索条件にする（identity 用）
- Knowledge から空き枠を読む
- 上位1件だけを絶対視する
- ②ヒットをユーザーへの思想説明に使う

## 7.4 実相談での実績（参考）

`scripts/test_notes_knowledge_rag.py` では、思想を直接聞かなくても、

- 「腰を温めたら」→ `notes_body_connection` が1位
- 「鍼と整体どっち」→ `notes_approach_candidates` が1位、`notes_suggestion_stance` も候補
- 「相談だけ」→ `notes_reservation_intent` が候補（1位は公式予約方法になる場合あり）

会話層では、1位が公式でも、選んだ notes をコンテキストに残す。

# 8. 回答生成の考え方

## 8.1 入力

1. **常時ルール（system）**  
   診断しない、保証しない、捏造しない、CTA毎回禁止、質問は1〜2、緊急時は医療優先、標語の連打禁止
2. **会話履歴**（直近を上限付きで）
3. **状態**（部位、期間、目的、予約意思、既出の質問）
4. **RAG**  
   ①は事実として引用可。②は内部方針。③は一般知識（あるときだけ）
5. **予約システム結果**（空き確認ターンのみ）

## 8.2 ②の載せ方

ユーザーに「Knowledgeによると身体はつながっています」と説明しない。

モデルへの指示例：

> 局所＝原因と決めない。周辺・姿勢・動作の可能性として触れてよい。原因断定はしない。

## 8.3 公式事実

料金・時間・キャンペーン・院内可否は ① に無いなら「現在の情報では確認できない」。推測で埋めない。

## 8.4 スタイル

- 親しみやすい、落ち着いている
- 専門用語を並べすぎない
- 断定しすぎない（「〜のこともあります」「今の話だけなら候補」）
- スマホで読める長さ（目安：短めの段落2〜4）
- 絵文字は多用しない
- 「身体はつながっている」は、そのターンで意味があるときだけ自然に使う

## 8.5 生成後検査

- ①にない円額・キャンペーンを作っていないか
- 「必ず治る」「原因は○○」がないか
- 疑問符の追加質問が多すぎないか
- 相談専用ターンで予約URLを付けていないか

# 9. 追加質問のルール

問診票にしない。1回あたり原則1〜2個。聞く理由があるものだけ。既出は聞かない。答えられることは先に答える。

## 9.1 優先して聞いてよいこと（身体相談）

- いつ頃からか
- どんなとき（座位、動作、朝夜）
- 目的（楽になりたい、動き、美容、パフォーマンス）

年齢・職業・既往の全列挙はしない。

## 9.2 悪い例 / 良い例

悪い例（腰が痛いです、への返答）：いつから／どこが／何をすると／何歳／運動／仕事／既往を一度に聞く。

良い例：短い整理のあと、「いつ頃からですか。座っているときと動いたときで違いはありますか。」

## 9.3 状態

`asked_questions` と `known_slots` を持ち、同じ質問を繰り返さない。

---

# 10. 施術提案のルール

`症状A → 施術B` の固定表は作らない。

- 候補として出す
- 「今の話だけなら〜が候補になりやすい」
- 最終は状態を見て判断する、と残す
- 効果保証しない
- メニュー名・料金・可否は①。②は考え方だけ

例（腰＋鍼か整体）：どちらが正解とは言わない。目的と出方で候補が分かれること、もう少し教えてほしいことを伝える。

トータルコンディショニングは個別サービス名ではなく、予約上のコース名称（①の事実）。②で別定義しない。

---

# 11. 相談→予約への遷移

## 11.1 相談が先

「相談だけ」「まだ決めてない」→ 予約方法の説明や「ご予約はこちら」を出さない。相談に答える。② `notes_reservation_intent`。

## 11.2 予約へ切り替える合図

- 予約したい
- 受けてみたい／見てもらいたい（施術意思が明確）
- 空きを知りたい

このとき既存予約フローへ。AIが空き判定ロジックを持たない。

## 11.3 CTA

全回答に付けない。相談専用・情報専用・一般健康では付けない。

遷移後は `/book` や公式LINEなど、①の予約方法に沿う。帯同・法人は Web即予約しない、も①に従う。

# 12. リアルタイム予約システムとの境界

| | 役割 |
|---|---|
| Knowledge | 営業時間の目安、12時間前、チャネル、院内準備中などの公開事実 |
| 予約システム | その日時が空いているか、確定 |

「明日の夜空いてますか？」→ 営業時間Knowledgeだけで「空いています」と言わない。  
`/api/book/dates`・`/api/book/slots` 相当を使う。ロジックは複製しない。

エリア・時間・コースが足りなければ、空きAPIの前に1〜2個だけ聞く。

AIは枠の○×計算を再実装しない。

---

# 13. 会話履歴の扱い

## 13.1 持つもの

- 直近メッセージ（上限。目安10往復程度）
- 要約してよい既知事実：部位、期間、誘発、目的、予約意思、相談のみ
- この会話で既にした質問

## 13.2 持たない／慎重に扱うもの

- カルテ化（診断名、詳細な病歴の永続保存）は初期実装ではしない
- 決済情報
- スタッフsessionと混在させない

## 13.3 保存場所（実装時に決定）

初期はサーバー側の短寿命セッション、または会話ID＋サーバ記憶で足りる。  
個人情報を長く残す設計は、UI実装時に別途決める。

履歴が切れても、安全ルールと公式事実の捏造禁止は維持する。

# 14. 具体的な会話例

以下は設計上の望ましい応答例である。実装済みの出力ではない。

---

### ケースA：症状相談

ユーザー：  
腰が痛いです。

AI：  
腰がつらいんですね。つらい場所だけを見るより、動き方や姿勢、股関節まわりの使い方など、まわりの状態も一緒に考えることがあります。

今の時点で「この施術が必要」とは決めません。  
いつ頃からなのか、座っているときと動いたときで違いがあるか、教えてもらえると整理しやすいです。

（予約CTAなし。診断なし。質問は2個以内。）

---

### ケースB：セルフケア相談

ユーザー：  
腰が痛いので、腰を温めたら良いですか？

AI：  
温めて楽になることもあります。ただ、腰の痛みは腰だけとは限らず、股関節まわりの動きや姿勢、普段の動作が関係していることもあります。

原因をここで断定はできません。  
温めながら様子を見るのは一つの方法ですが、急に強くなった、脚のしびれがひどい、といった変化があれば医療機関の相談も検討してください。

いつ頃からですか。動いたときと安静のときで違いがありますか。

（「股関節が原因です」とは言わない。）

---

### ケースC：施術選択

ユーザー：  
腰が痛いんですが、鍼と整体だったらどっちがいいですか？

AI：

# 16. テスト方針

既存の読み取り専用 RAG テストは維持する。会話実装後も `test_ai_knowledge_rag.py` に INSERT/UPDATE を戻さない。

会話テストは TEST_SPEC の SERVICE / BOOK / SAFE / CATEGORY を会話品質として使う。

| 観点 | 見ること |
|---|---|
| 症状相談 | メニュー断定しない。body_connection の見方が自然に出る |
| セルフケア | 温め等に全部否定せず、局所だけに固定しない。原因断定しない |
| 施術選択 | 候補。固定マッピングしない |
| 未決定 | 1〜2問。整体を即推ししない |
| 相談だけ | CTAなし |
| 予約したい | 予約導線。空きはAPI |
| 空き | Knowledgeだけで「空いている」と言わない |
| 緊急 | 医療優先。予約しない |
| 肩こりのみ | 自動で病院に送らない |
| 料金 | ①のみ。無いものは確認できない |
| ターン変化 | 相談→予約へ切り替わる |

自然文を使う。Knowledgeタイトルをユーザーが言う前提にしない。
